How to adopt the kit and get your first story shipped

What Is This Kit?

A portable, harness-agnostic set of process docs, role specs, and templates — copied into your repo so any AI coding agent works your initiatives the same way.

Not an app

No source code here — every file is Markdown: process, roles, templates.

Harness-agnostic

Works with Claude Code, GitHub Copilot, OpenCode, Codex, and others.

Copy, don't fork

You copy the kit files into your own repo — this repo just ships them.

What Changes For Your Team

Two connected stages replace ad-hoc, chat-driven development:

Optional

Discovery

Brainstorm a PRD, break it into BRDs (one per Epic), then design a Spec and HLD for each — each stage gated on human sign-off.

Orchestrator-driven

Delivery

A fixed loop: BA grooms stories → Developer implements → Reviewer verdicts → QA validates — looping on failure, escalating on repeat blockers.

Two Properties That Matter Most

Nothing merges without evidence.

Build-verify must be GREEN, Reviewer must APPROVE (zero P1/P2), QA must PASS every AC — or a human explicitly waives it.

Review and QA are adversarial by design.

Both run in a fresh session that never inherited the Developer's conversation — checking the diff cold, not confirming what they were told.

You don't have to use every stage — see "Ways to Enter the Loop."

Delivery: The Orchestrator Loop

Pick next queue item — groomed story exists? No → ba.agent grooms it. Yes → skip straight through.

developer.agent implements — fresh context per story, test-first, build-verify gate

reviewer.agent (fresh, isolated) — APPROVE → QA  |  REQUEST_CHANGES <2 cycles → back to Developer, ≥2 → escalate to human

qa.agent (fresh, isolated) — PASS → close story, next one  |  FAIL → back to Developer

Step 2 — Fill In project-context.md

Repository

GitHub URL, and this project's commit message format — developer.agent reads this instead of a hardcoded convention

Delivery Tracker

Jira / GitHub Issues / Local docs — every role file reads this to know where stories live

Step 3 — Add Project Skills (optional)

3

Engineering-standard rules per skill.template.md — security, db conventions, logging, whatever your project needs.

  • Add directly at your harness's skill location (e.g. .opencode/skills/<slug>/SKILL.md) if built via build-kit.sh — docs/skills/ only if hand-copied without a native mechanism
  • Your harness discovers it there on its own — developer.agent.md/reviewer.agent.md never name a skill path, so there's nothing to keep in sync
  • A real Agent Skills SKILL.md (frontmatter: name, description) — no kit-invented Owner/Meta fields
  • No role tag — skills are agent-agnostic
  • No forced-load flag — any agent judges every skill's relevance to the task at hand

Step 4 — Wire Into Your Coding Agent

Guaranteed everywhere: point your agent at a file directly — "follow AGENTS.md." On top of that:

Read This First

Gotchas

A few things worth knowing up front

Gotchas Worth Knowing Up Front

Asymmetric circuit breaker. Reviewer↔Developer caps at 2 REQUEST_CHANGES cycles before escalating; QA↔Developer has no cap today. Known and intentional.

Hard rule vs. default. Reviewer/QA's fresh-context isolation is a hard rule — it's what makes the gate meaningful. Developer/BA's is a default a harness can skip for convenience.

Templates stay stack-agnostic. Project-specific facts belong in docs/project-context.md, never hardcoded into a role file.

Copilot has no native skill discovery. Claude Code/OpenCode/Pi/Codex all auto-discover skills from their own folder, so role files never name a skill path. Copilot needs an explicit nudge — build-kit.sh puts one in copilot-instructions.md; wiring by hand means adding it yourself.
